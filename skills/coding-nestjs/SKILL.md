# NestJS 服务端编码规则

## 角色

约束 NestJS 服务端代码的实现、迁移、审计、事务和验证方式，避免本地可运行但生产不可上线的变更。

## 约束

### 适用范围

- 具体服务路径由项目 `.agents/skills-config.json` 的 `coding.nestjs.paths` 定义。

### 安全约定

- 不在代码中写死生产密钥、域名或对象存储凭据，配置统一走 `.env` 或 `deploy/*.env`。
- 非公开接口默认要求鉴权。
- JWT strategy 的 `validate()` 返回值必须同时暴露 `id` 与 `userId`，避免业务控制器因服务拆分后 payload 字段不一致而丢失操作人。
- 控制器读取操作人时使用显式类型或 helper，优先 `userId`，兼容 `id`，不要在业务方法里散落 `req.user.id` 假设。

### 数据库与迁移

- 生产环境禁止依赖 ORM 自动同步 schema；schema 变更通过 migration、SQL 脚本或明确的数据变更步骤管理。
- 影响数据库 schema、初始化 SQL、历史数据回填、RBAC 初始化的数据变更，都按需迁移处理。
- 新增或修改 entity 后，必须同步检查 migration、初始化 SQL 或脚本、部署预检与回滚路径。

### 精度、审计与事务

- 涉及价格、数量、重量、尺寸等字段时，必须明确单位与精度，避免隐式浮点换算和不带单位的字段扩散。
- decimal 运算统一按两位小数语义安全计算，禁止直接字符串拼接数字。
- 所有写操作必须记录审计日志。
- 每次新增功能、接口或关键业务流程时，必须评估是否需要补充操作日志；涉及库存、配置、权限等变更默认优先考虑记录。
- 涉及多表写入的操作必须使用事务，保证数据一致性。

## 工作流

### 1. 定位服务和影响面

- 根据用户请求和 `coding.nestjs.paths` 确认目标服务、模块、控制器、service、entity 和 migration 影响范围。
- 标记是否涉及鉴权、RBAC、库存、订单、价格、数量或跨表写入。

### 2. 设计变更路径

- 先明确配置来源、鉴权入口、操作人字段、事务边界和审计日志写入点。
- 涉及 schema 或数据变更时，同步规划 migration、初始化脚本、预检和回滚路径。

### 3. 实施代码

- 沿用现有 NestJS 模块、依赖注入、DTO、guard、service 和 repository 模式。
- 对新增或修改的写操作补齐审计日志和事务处理。
- 对金额、数量、重量、尺寸等字段保持单位和精度语义清晰。

### 4. 验证

- 具体命令以项目 `.agents/skills-config.json` 的 `coding.nestjs.verifyCommands` 为准。
- 通用验证包括全局 lint、build、单服务 build、单元测试。
- 涉及鉴权、RBAC、库存、订单等关键变更时，必须补或更新对应测试用例。

## 输入

- 用户指定的服务端功能、Bug、接口、数据结构或迁移需求。
- 项目 `.agents/skills-config.json` 中的 `coding.nestjs` 配置。

## 输出

- 符合 NestJS 项目约束的代码、测试和必要迁移文件。
- 对迁移、回滚、审计日志、事务和验证命令的简明说明。

## 自检

- [ ] 未硬编码生产密钥、域名或对象存储凭据。
- [ ] 非公开接口有鉴权，操作人字段兼容 `userId` 和 `id`。
- [ ] schema 或数据变更已配套 migration、初始化脚本或明确步骤。
- [ ] 金额、数量、重量、尺寸字段单位和精度清晰。
- [ ] 写操作已记录审计日志，多表写入已使用事务。
- [ ] 已按项目配置运行必要 lint、build 或测试。
