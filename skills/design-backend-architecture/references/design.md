# 后端设计决策与示例

## 1. 模块、分层与依赖

按业务能力组织模块，名称与现有项目一致，目录表达职责。下表描述边界，不强制每个模块建同样目录。

| 边界 | 负责 | 不应承担 |
|---|---|---|
| Controller／传输适配 | 路由、DTO 校验入口、认证上下文、协议映射 | 业务算法、直接拼 SQL、编排多表写入 |
| 应用服务／用例 | 编排业务操作、授权上下文、事务、幂等、审计协调 | 堆积所有领域的规则、感知前端交互细节 |
| 领域对象／业务服务 | 规则、状态、不变量和业务计算 | HTTP 状态码、请求对象、ORM／远程协议细节 |
| Repository／基础设施适配 | 查询、持久化、外部依赖与结果转换 | 决定整条业务流程或吞掉业务失败 |

入口调用用例，用例依赖业务规则和必要的存储／外部能力；复杂领域核心不反向依赖 Nest HTTP 或 ORM。只有确有隔离变化、替换实现或测试业务契约的需要，才为基础设施引入端口；运行时依赖绑定由框架适配入口负责，业务核心保持独立。

简单单表 CRUD 可用 Controller → Service → ORM Repository，规则仍在 Service 内聚。规则复杂、跨对象流程或多实现时，再拆用例、领域与适配器。不为一行转发复制三套 DTO，不提前建设全项目 BaseRepository。模块通过公开服务／契约协作，不跨模块读取内部 Repository 来绕过业务规则；若确有报表读模型，明确其只读权限与归属。循环依赖应先查职责，框架的循环依赖机制不能替代边界设计。

## 2. 面向对象、封装与命名

- 对象通过有业务含义的方法维护不变量，避免可变字段公开后任意写入；规则可用内聚业务对象或纯函数表达，不为类型数量而创建空壳类。
- 优先小接口与组合。只有可替换行为／边界才抽接口；继承必须满足替换语义，避免为复用两行代码形成巨大基类。
- 应用服务面向用例命名，方法表达动作与对象；类型／DTO PascalCase，方法 camelCase，布尔 `is/has/can`。模块、文件、路由及错误码形式遵从项目规范，业务术语保持一致。
- 查询方法命名体现范围与返回语义，如分页结果与可能不存在的单条结果；查无数据、权限不足、依赖失败不能共享模糊的 `null`／`false`。
- 拆分依据业务职责、变化与可理解性；不按固定行数、重复次数或未来猜想强制抽离。

**反例**：`OrderService` 同时处理导入、库存、支付、报表、HTTP 错误和邮件发送；所有模块继承可绕过权限的万能 CRUD Service。

**正例**：提交订单用例协调价格校验、库存预留和持久化；订单规则集中表达。只读单表字典维护保留简洁 Service，无需领域工厂与策略体系。

## 3. DTO、接口与类型边界

- 对外输入需要真实运行时校验，TS 类型不能替代验证；核实项目全局 ValidationPipe／转换配置实际生效。路径、查询和 body 均校验，分页／批量大小设上限。
- DTO 只允许本操作可变字段，禁止 `save({...body})`／把客户端对象直接赋给 Entity；用户身份、角色、归属、审核状态等由可信上下文或明确业务动作决定。
- Create／Update 区分缺失、null、空字符串、零值与部分更新语义；ID、枚举、日期／时区、数量单位和 decimal 序列化写清契约。
- Entity 是持久化结构，响应使用明确投影／响应模型，禁止自动暴露密码哈希、内部标记或关联的敏感字段。字段无变化且语义相同可以共享类型，不机械复制。
- 接口围绕资源和任务建立稳定契约，明确筛选／排序白名单、分页、错误码与写操作幂等语义；兼容变更核查网关及所有调用方，破坏性变化遵守项目版本策略。
- 权限在服务端执行：鉴权之后检查功能、对象／租户／组织／仓库范围及敏感字段。不能把客户端传入的范围参数当成权限证明。

## 4. 状态、事务与并发

为关键业务列出“当前状态 + 动作 + 前置条件 → 新状态 + 副作用”，拒绝非法迁移。用枚举／联合类型和明确操作表达状态，避免大量独立布尔造成不可能组合。

- 持久业务状态由数据库和业务规则维护；请求身份／事务上下文仅在本请求使用；缓存是有失效策略的派生副本。禁止在单例 Service 字段保存当前 user／request／transaction。
- 同库原子步骤使用同一事务 manager／连接；事务内拿普通全局 Repository 会逃逸事务。明确隔离级别、锁顺序与冲突处理，不默认“开启事务即无并发问题”。
- 通过唯一约束、条件更新、版本号或必要行锁保护不变量。先读后写必须说明竞争窗口如何关闭；读取旧值用于审计或计算时也需保证其与实际写入一致。
- 幂等键绑定授权主体、操作及请求语义，持久保存结果或执行状态；相同键不同载荷按契约拒绝。前端禁用按钮不能代替服务端幂等。
- 本地事务不覆盖远程调用。需要跨系统可靠协作时评估事件／outbox／补偿，先写清一致性要求再选机制；不要在普通 CRUD 强制引入分布式架构。

库存扣减的职责示意（不是可直接运行的接口）：

```text
Controller: 校验扣减 DTO，从可信上下文取 actor
Use case: 验证 actor 对仓库／物料的访问范围，校验数量与幂等键
Transaction:
  按唯一约束认领本次操作，重放合法的已完成结果
  UPDATE 库存 SET 可用量 = 可用量 - :qty
    WHERE 仓库 = :authorizedWarehouse AND 物料 = :item AND 可用量 >= :qty
  检查受影响行数；未更新按契约返回不存在／状态冲突／不足
  同一事务写业务明细、成功审计与幂等结果
Boundary: 业务失败映射稳定错误码；未知故障回滚并保留关联标识
```

这里 :qty 必须已校验为合法正数量；具体锁、约束和 SQL 以项目数据库能力为准。不能靠“先查余额，再保存新余额”保证并发安全。

## 5. 错误边界与日志

| 类别 | 责任与映射 | 恢复原则 |
|---|---|---|
| 输入／校验错误 | 传输边界报告字段和合法格式 | 调用方修改输入 |
| 预期业务失败 | 规则／用例产生稳定业务码，由边界映射项目响应 | 按业务改状态／参数或重新获取事实 |
| 授权／资源不可见 | 统一认证与数据范围检查 | 遵守项目信息披露策略，不暴露越权对象存在性 |
| 数据库／外部依赖故障 | 基础设施保留 cause，边界映射可安全响应 | 仅满足幂等且可恢复的错误有限重试 |
| 未知缺陷 | 统一异常边界记录必要上下文与关联 ID | 返回安全故障，不误报成功 |

业务核心避免依赖 HTTP exception；简单 Service 若沿用项目应用层异常模式，可在该层使用项目既有异常，不为此强拆空层。错误码、响应 envelope、日志入口复用项目实现。业务错误与未知故障不能同等打印堆栈；禁止逐层 catch/log/rethrow 重复上报，禁止泄露 SQL、凭据、个人敏感信息。审计描述成功业务事实，技术诊断描述故障，两者职责不同。

**反例**：所有异常 catch 后返回 `[]`／`true`；失败统一改成“找不到记录”；每一层重复打印完整请求和堆栈。

**正例**：查询无结果返回合法空分页，查询失败抛有 cause 的依赖异常；写入冲突返回稳定业务码；由一个适当边界记录未知故障并返回关联标识。

## 7. 验证选择

按改变的不变量验证正常与失败路径：越权范围、DTO 字段、非法状态、并发扣减／重复提交、事务回滚、审计一致性、分页与 N+1。纯业务逻辑可单测，数据库约束／锁／真实事务需隔离数据库验证；mock Repository 无法证明它们。性能结论附实际查询与测量条件，未执行数据库验证或性能测量时明确限制。

数据访问细则的唯一维护入口为 [数据库读写](database.md)，查询、持久化、并发或批量操作变化时必读。
