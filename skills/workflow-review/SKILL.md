# 评审协议（workflow-review）

## 1. 定位与方法论

> 用户原话定调：「我让 review 的时候一般都是两个环节，一个推进到研发设计完成环节，一个是推进到 test passed 环节，然后 review 我都是直接从 0 review，不信任版本或者需求输出的任何一个文件，从头到尾的进行 review」；「应该按照各个需求的生命周期环节逐项 review，不同环节有不同的侧重点」。

- **零信任、从 0、从头到尾**：需求产出的所有文件（TECH_DESIGN / IMPLEMENTATION_PLAN / ACCEPTANCE / CHECKLIST / TEST_EVIDENCE / MIGRATION / BACKLOG 状态与备注）、以及**此前轮次的评审结论**，一律视为"待验证的主张"，不是事实来源。评审者自建事实基底：读代码（file:line 亲核）、查数据库、跑命令、点 dev 环境、对照真实单据。
- **逐环节推进**：按该需求已到达的生命周期环节，从 ⚪ Todo 走到当前环节，每环节用该环节的考察清单过；**不因"已过该环节"而豁免**——Test Passed 评审覆盖设计完成评审的全部范围（设计已内化于实现），L1 在后置停点不跳过。
- **委托点**：通常为「研发设计完成」（编码前）或「Test Passed」（合并/发布前），但协议是全链走查；复审同样全量从 0（增量视角会漏掉修复自己引入的新问题，F-228 R08/R18 教训）。
- **文档对账**：主张 ↔ 实际逐条比对，不一致本身就是发现。

## 2. L0 · 需求合理性分析（每次评审的开场，先于逐环节走查）

- [ ] **真实性**：需求源自真实业务事实（真实单据/工厂流程/用户实际操作记录），能指出具体出处；技术臆想、竞品模仿类需求要挑战
- [ ] **必要性**：不做会怎样？显式考虑过"不做的解法"（删/藏/以后再说——板材独立区块被"Excel 里没有"一句话否掉）
- [ ] **对症性**：解决的是问题本身还是症状？警惕手段当目标（"加个字段"背后可能是模型错位）
- [ ] **方案量级匹配**：小问题大方案=过度设计；大问题打补丁=欠设计；方案选择表里的否决项是真实比较过的，不是稻草人
- [ ] **代价显性化**：新增概念/字段/入口都是要还的债，写清"谁维护、何时用"

## 3. 生命周期环节 × 考察点矩阵

对被评审需求逐环节过；带 📌 的为该项目历史教训锚点。

**⚪ Todo 登记**
- [ ] BACKLOG 行状态值取自法定集合（出过 `✅ Released` 类野写法）
- [ ] 迁移声明覆盖四类触发（schema/初始化 SQL/历史回填/RBAC 初始化）并与改动一致；范围扩大时同步改（B-238 否→是先例）
- [ ] 资源声明（services/files/tables）覆盖实际 changed paths，无跨需求冲突
- [ ] 独立 branch + worktree 已建、已推远端、版本绑定正确（bump/join 计算）

**🔍 Reviewing**
- [ ] 需求一句话可复述，验收方与实现方口径一致
- [ ] 拆分判断：同文件重叠不拆并行（B-238 单需求先例）；跨域低耦合该拆未拆也要指出
- [ ] 不夹带"以后再说"的范围蔓延项

**📝 Req Confirmed**
- [ ] 用户拍板逐条对照原始记录（对话/验收清单）核对转译忠实度，无擅自增删
- [ ] "不做什么"清单显式存在
- [ ] 每个验收场景可执行、可判定通过/失败
- [ ] 业务事实有锚点（真实单据/工厂流程引用）

**🧩 Tech Design**（另过 §4 设计准则组）
- [ ] 方案选择表存在，含被否决方案及理由
- [ ] 设计者自决项显式列出（R 清单模式，B-238 的 R1-R5），逐项给理由与风险
- [ ] 契约：schemaVersion 策略、旧数据/旧客户端处置（409 门禁）、类型定义与现行 DTO 差异逐字段列明
- [ ] 迁移：表/列/约束/索引、回滚命令级、schema.sql 同步、回填与否及理由、dev 数据处置
- [ ] 消费端完整性逐项过：gateway 路由 / admin / web / Excel 导出 / 打印 / E2E / 报表 / RBAC
- [ ] 可行性亲核：引用的每个 file:line 打开核对；"复用现有机制"验证机制真的存在（V1 快捷新增被 V3 弄丢）；数据库现状主张查库实证（"prod 零数据"→ 查）
- [ ] 五件套齐备；CHECKLIST 的 P0/P1 证据是真实产物不是自勾
- [ ] manifest 服务并集正确；测试策略分层覆盖全部验收场景；波次计划到文件级

**🔨 In Dev**（另过 §4 编码准则组）
- [ ] 变更面 diff 从头到尾通读（不抽样）；无非目标文件误改（BACKLOG 投影漂移之外）
- [ ] 实现与设计一致；偏离处回写了设计文档
- [ ] lint/build/单测**本轮亲自跑**，不信"之前跑过"
- [ ] 范围变化同步了 BACKLOG 备注 / manifest / MIGRATION 草稿
- [ ] 红绿纪律：每个 bug 修复必带"修复前会失败"的复现测试；禁止删测试/跳过测试换绿

**🚚 Dev Deployed**
- [ ] dev lease 持有且与需求同版本（takeover 规则合规）
- [ ] 部署 commit 可从绑定分支可达、ref 已推远端（先 ff 再发的教训）
- [ ] deployment snapshot 不可变；HEAD 相对快照仅 BACKLOG 投影漂移
- [ ] 内置 smoke 通过；共享 dev 造数已清理

**🧪 Testing**（另过 §4 测试准则组）
- [ ] ACCEPTANCE 场景逐条有对应测试，含边界/异常路径
- [ ] 新增 E2E 场景补了 cleanup 自清理才可入 @smoke-dev；定位器健壮（antd v6 教训）
- [ ] 集成测试用 IT_DB_* 显式隔离凭据，禁止回退业务库（DROP USER 事故）
- [ ] TEST_EVIDENCE 记录真实命令+输出，testedCommit 显式提交（禁 checkout 恢复）
- [ ] 修复轮做回归对照，防"修 A 坏 B"

**✅ Test Passed**
- [ ] testedCommit == 分支 HEAD；快照锚点一致
- [ ] 关键测试套件重跑，识别 runner 假绿（退出码/输出真伪/skip 清单为零）
- [ ] entities ↔ schema.sql ↔ 实际库三方对账（schema 漂移教训）
- [ ] 对照上一版本逐功能比对抓退化（V1→V3 功能丢失类）
- [ ] release 文档/CHANGELOG 与实际变更对账；preflight 结果亲验
- [ ] 出合并就绪三态结论

**📋 Prod Planning**
- [ ] 迁移执行方案：顺序/窗口/备份（凭据获取方式）/中断处置
- [ ] 回滚预案命令级可执行
- [ ] 发布文档成稿；列车成员与合并顺序约束对齐
- [ ] dev 成功快照在 prod 侧可达（跨机 scp 教训）
- [ ] **备份可恢复性验证**：恢复演练或至少校验备份文件非空有效（20 字节假备份=没备份）

**🚀 Prod Deployed**
- [ ] 用户明确批准在案（红线，不可代理）
- [ ] tag / 镜像 digest / manifest 三对齐
- [ ] 备份先行；迁移逐条验证；prod smoke 通过；回滚触发条件明确

**✔️ Done**
- [ ] completion 闭环（COMPLETION.json + plan-completion 锚 main tip + PR）
- [ ] 文档归档到位；lease 释放；worktree 清理；BACKLOG 终态合法

**版本级横切（列车多成员时）**
- [ ] manifest 服务并集、成员依赖与合并顺序、共享快照一致性、全员 completion 对齐

## 4. 质量准则组（三组，对应环节引用）

### 4.1 设计准则（🧩 Tech Design）

- [ ] **高内聚低耦合**：模块边界图存在、依赖方向单向（domain 不依赖框架、UI 不绕过 reducer 直连 API、服务不反向依赖前端——F-235 分层先例）
- [ ] **单一职责**：服务/类职责膨胀检测（drafts.service 越长越大的教训：新领域规则必须提取独立模块）
- [ ] **真源唯一**：每份数据只有一个权威来源；双真源一致性校验是设计坏味道（板材"板材行↔材料行比对"被作废的先例）
- [ ] **契约显式**：类型、错误码、定位信息（到字段级）都在契约里，不靠约定
- [ ] **事务/幂等/竞态**：边界写明；异步回填竞态保护（过期请求不覆盖手工输入）
- [ ] **可逆性**：休眠优于删除（阶段字段隐藏先例）；迁移必须带回滚
- [ ] **YAGNI 与扩展点平衡**：为已知的未来留口，不为想象的未来建结构
- [ ] **性能边界**：行量放大、分批、上限（材料变体粒度 2000 行量级的考虑方式）
- [ ] **安全**：权限最小化、泄漏路径排查（报价不出现在任何无权限载体——R12 先例）

### 4.2 编码准则（🔨 In Dev）

- [ ] **高内聚低耦合**：跨层直连检测、循环依赖、上帝类/上帝函数
- [ ] **职责单一与体量**：函数/类过长即拆分信号
- [ ] **DRY 与过早抽象平衡**：三处重复才抽象，两处容忍
- [ ] **错误处理完备**：异步副作用必须 try/catch 且失败不静默吞（Admin 教训）
- [ ] **类型安全**：契约类型走共享 domain 包，禁局部重复定义、禁 any 填坑
- [ ] **注释纪律**：只写代码表达不了的约束，不写"对 reviewer 的话"
- [ ] **可测性**：领域逻辑纯函数化（无 IO），reducer 不碰网络
- [ ] **退役清理**：删概念就删干净，不留死代码死校验（板材校验连根拔先例）

### 4.3 测试准则（🧪 Testing）

**通用单测**
- [ ] F.I.R.S.T.：快、独立、可重复、自验证、及时
- [ ] 确定性：时间/时区/随机数/网络受控——冻结时钟、固定种子、mock 边界外 IO（跨午夜日期 bug 教训）
- [ ] AAA 结构 + 单一行为；命名 "should X when Y"，失败信息即规格
- [ ] 边界值必测：等价类 + 边界（null/空/0/负/超限/非法枚举）
- [ ] 断言精确：期望值写死具体值，禁 toBeTruthy/toContain 类宽松断言
- [ ] Mock 只打在架构边界（DB/网络/时钟），不 mock 内部实现
- [ ] 覆盖率是信号不是目标：核心域高覆盖，不为数字凑测试

**Flaky 政策**
- [ ] 不稳定测试隔离 + 限期修复，不许静默重试掩盖

**分层策略**
- [ ] 领域纯函数单测为底座 → 服务层集成测关键路径（真实 DB+迁移）→ E2E 只测业务主流程；慢测试分层隔离

**集成**
- [ ] 一次性隔离库；迁移升降级都测（不只测 up）
- [ ] 隔离凭据显式（IT_DB_*），禁回退默认连接
- [ ] 测试自建数据自清理，无跨测试残留

**前端组件 / E2E**
- [ ] 组件测试按用户视角查询（role/aria-label，不用 className/内部 state）
- [ ] E2E 定位器用确定性锚点（aria/data-*），不依赖渲染文本；不 sleep，等确定性条件
- [ ] E2E 造数走 cleanup 自清理；进共享 @smoke-dev 前先补清理
- [ ] 快照测试克制使用，大快照=变更噪音

## 5. 六个专项审查块（横切，任何环节适用）

### 5.1 安全与权限
- [ ] 新端点/页面/操作逐一核对 RBAC 权限码，权限最小化
- [ ] 水平越权：按 ID 直查的接口逐个试（A 的单据 B 能不能看）
- [ ] 敏感数据（价格/成本/客户资料）全投影点枚举：列表/详情/导出/日志/错误信息/前端 state（R12 泄价先例）
- [ ] 服务端权威校验——绕过前端直接打 API 试试
- [ ] 注入面：SQL、Excel 公式（消毒先例）、上传类型
- [ ] 凭据不入库不入日志；日志脱敏；暴露面加固（hl-prod 被扫描待加固）

### 5.2 数据完整性与一致性
- [ ] DB 层约束（唯一键/外键/枚举）与应用层校验双向一致——只在一层有=漂移温床
- [ ] 快照不变性边界：主数据后续演化不影响历史单据（色卡改名先例）
- [ ] 软删/停用引用完整性：被历史引用的停用对象不可物理删
- [ ] 并发：乐观锁版本号在契约里且真被校验
- [ ] 金额/数量定点字符串禁浮点；时区统一 Asia/Shanghai
- [ ] 数量守恒对账闭环：下单→采购→入库→领料→发货，数量账对得平

### 5.3 UX 工程化（员工视角的落地版）
- [ ] 三态完备：加载/错误/空（下拉无候选、列表无数据时像坏了吗）
- [ ] 提交中禁用防双击；每个动作有反馈
- [ ] 错误文案可行动（"失败，因 X"而不是"失败"）
- [ ] 危险/不可逆操作有确认（保存到档案、发布）
- [ ] 文案说人话：黑话检测制度化（阶段/板材/建议清单被砍的先例）
- [ ] 高频操作效率路径：自动带入、默认值、批量操作——点击次数就是成本

### 5.4 协作与 AI 产出事实核对
- [ ] 交接/记忆/文档里的声称逐条核实（F-235 交接两处失实教训）
- [ ] agent 写的"已完成/全绿"声明 vs 实际 diff、实际命令输出对账
- [ ] 幻觉 API：评审必须编译/运行验证，不能只读代码
- [ ] 越权红线核对：生产迁移/部署/回滚有用户明确批准在案
- [ ] 批量 subagent 同构产出抽验（防同质化错误批量复制）

### 5.5 性能
- [ ] N+1 查询检测（TypeORM 高发）
- [ ] 列表接口必分页（零件分类超 100 不可达的隐患同型）
- [ ] 索引 vs 查询条件核对
- [ ] 前端大数据量渲染（合并显示/虚拟滚动/防抖搜索）
- [ ] 上限与降级路径：超限时的行为明确（拒绝/截断/分批）

### 5.6 可运维性
- [ ] 结构化日志：关键路径有日志、错误带定位信息、级别合理
- [ ] 健康检查/部署后验证覆盖新功能
- [ ] 迁移中断半态恢复方案（幂等或可续跑）
- [ ] 部署前磁盘预检（AGENTS 既有约定的执行核对）
- [ ] 回滚不是纸面预案：触发条件+执行步骤可操作

## 6. 五透镜（贯穿所有环节的视角）

1. **员工视角**：看不懂即缺陷——黑话、三态勾选、隐藏模式都是红旗
2. **业务实证**：真实单据/工厂流程为准绳，技术合理性让位
3. **版本退化**：对照上一版逐功能比对，"以前有现在没有"默认退化
4. **数据模型贴业务真形**：存储锚定最细主体，展示才合并
5. **删繁就简**：拿不准就删/藏，"以后要了再加"

## 7. 严重度与结论口径

- **P0**：阻断发布/数据风险/安全漏洞 —— 不可继续
- **P1**：必须修复后再发布 —— 需修复
- **P2**：可跟踪改进 —— 可继续带病
- 结论三态：可继续 / 需修复后再评审 / 不可合并
- 每条发现标注 **亲证 / 推断**（亲证=亲眼见代码或复现；推断=逻辑推演待验证）

## 8. 产出模板

```markdown
## 评审报告：<需求 ID> @ <停点>（基线 commit）
### 结论：可继续 / 需修复后再评审 / 不可合并
### 发现清单
| # | 严重度 | 环节 | 主张 vs 实际 | 锚点(file:line / 命令输出 / 单据) | 亲证/推断 | 建议 |
|---|--------|------|--------------|-----------------------------------|-----------|------|
### 已核对无异议项（主张↔实际一致的要点，供下轮豁免参考但不豁免重审）
### 自决项复核意见（对 R 清单逐条）
```

## 9. 引用档（一行提醒，不复制内容）
