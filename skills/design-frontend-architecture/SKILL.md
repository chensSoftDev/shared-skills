# 前端架构与业务对象设计

## 角色

以前端架构师视角，将业务逻辑集中于内聚、可独立验证的纯TypeScript业务对象，明确职责、组合、状态、错误及生命周期。框架视图通过适配器使用对象；目标架构在新增和实质修改范围内增量应用。

## 上下文与约束

读消费项目AGENTS、已有业务模块与调用方；项目差异从skills-config的既有coding配置及真实依赖识别，缺配置不推定框架、语言、路径或新库。项目路径相对消费项目根，以下参考相对本skill。

- 非平凡业务功能默认先设计纯TS业务对象，以业务能力／任务划界，集中维护规则、合法状态及业务命令。纯函数可服务于对象内部计算或策略；Hook只适配框架，不重新承载业务规则。
- 对象不依赖React、DOM、路由、表单库、toast或具体HTTP实现；通过必要的小端口注入外部能力。优先组合，封装状态与不变量，不建立万能Manager或为类数量创造空壳。
- 明确谁持有对象、实例作用域、创建／切换／共享／释放、读写接口、快照及副作用边界。不得把用户／任务可变对象放入全局或SSR跨请求单例。
- 简单无业务含义的局部交互可用局部state；不强制每个布尔开关建立领域模型。抽象解决真实职责／变化，不按行数或未来猜想堆层。

## 工作流

1. 识别业务任务、规则、对象与现有公共能力，输出职责／依赖表；必读 [业务对象设计](references/business-objects.md)。
2. 为对象定义身份、输入、业务命令、合法转换、状态所有者与失败路径；必读 [状态与错误](references/state-and-errors.md)。
3. 以组合连接领域对象、任务会话与外部端口；UI只展示投影并发出命令。按项目框架入口处理订阅／表单适配，UI变化另用 [frontend-ui-quality](../frontend-ui-quality/SKILL.md)。
4. 在不挂载UI时验证对象规则与状态，再验证适配层的实例稳定性、请求竞态、失败恢复及实际交互。输出边界、抽离原因和真实结果，不宣称未执行的UI／性能验证通过。

## 输入与输出

输入：业务任务、状态／抽象问题及项目事实。输出：对象职责与公开契约、组合与数据流、状态／错误／生命周期设计及必要实现和证据。

## 自检

- [ ] 业务逻辑有清楚的纯TS对象归属，Hook／视图未重复实现规则。
- [ ] 公开命令、私有状态、不变量与依赖方向明确，对象规模匹配业务职责。
- [ ] 实例作用域、快照／订阅、请求身份、失败恢复与释放完整。
- [ ] 表单／URL／缓存／业务草稿没有相同语义的多份事实源。
- [ ] 可不依赖UI验证业务行为，简单功能没有被机械复杂化。
