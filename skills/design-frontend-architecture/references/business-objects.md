# 纯TypeScript业务对象

## 职责与依赖

| 边界 | 职责 | 公开能力 |
|---|---|---|
| 领域对象／值对象 | 业务规则、有效状态、计算和不变量 | 有语义的命令／查询，稳定只读快照或不可变新对象 |
| 任务／会话对象 | 编辑、选择、提交等任务编排，持有领域对象，协调端口和可恢复状态 | 任务命令、状态投影、必要订阅协议 |
| API／存储适配器 | 认证传输、契约校验、DTO转换与错误分类 | 实现业务所需的小端口 |
| 页面／视图 | 路由上下文、组装、呈现与交互 | props、事件和框架适配 |

默认先找业务概念，再找类。多字段订单编辑、报价计算、排产／库存任务等规则集中进对应纯TS对象；以OrderDraft、QuoteCalculator、OrderEditor等业务名称表达职责。一个简单任务可先在一个内聚对象完成，复杂规则与异步流程再分领域对象和任务会话，不强制所有场景两套类。

视图→任务对象→领域对象／端口，适配器实现端口；领域规则不反向依赖UI、HTTP或具体缓存库。模块通过小而明确的公开出口协作，不跨模块读内部可变字段。已有领域模型优先复用，不因页面不同复制规则。

## 封装与组合

- 构造／恢复时校验合法输入，操作通过addLine、changeQuantity、submit等业务语义表达；不把任意setState／setField、可变数组／Map或内部对象引用暴露给所有调用方。
- 使用private／#字段和只读接口维护不变量；只读TS类型不阻止外部JS修改，边界按需要使用防御性复制／深层不可变快照。不能每次读取都新建不同引用却声称快照稳定。
- 命令先校验再形成一次合法变化；失败不留下半完成状态。派生值由事实计算／缓存成投影，不通过多个effect维护副本。
- 对象可变或不可变都需明确语义：不可变对象返回新实例，由任务对象持有当前实例并发布变化；可变对象只通过命令更新，并提供稳定快照及清晰通知边界。
- 策略／外部能力优先小接口与组合；对象持有依赖而非自行查询全局容器。继承须有真正替换语义，不以BaseModel／万能Manager统一所有业务。
- 统一业务对象按能力集中规则，不按“整个前端”集中；订单、库存和登录不能共用一个全局可变对象。纯函数适合计算细节，规则入口及状态迁移仍有明确对象归属。

## 对象管理契约

| 项目 | 必须回答 |
|---|---|
| 身份／作用域 | 每任务、实体、工作区还是会话？哪些视图共享同一实例，哪些必须隔离？ |
| 创建／恢复 | 由谁创建、从什么DTO／快照恢复？构造器无I/O，不在render创建网络副作用。 |
| 读取／更新 | 谁拥有事实？公开哪些查询／命令？快照是否稳定、嵌套可变引用是否泄露？ |
| 订阅 | 谁发布变化、谁订阅、取消函数是什么？一次逻辑提交避免暴露中间状态。 |
| 异步／错误 | 请求绑定哪个任务身份／版本？迟到响应、重复提交、超时和失败草稿如何处理？ |
| 切换／销毁 | 切对象、关任务、页签保活、登出时分别保留／重建／取消／释放什么？ |

React的组件／Hook管理框架连接，对象管理业务生命周期；所有权不能因为有一个useXxx就被隐去。StrictMode重复挂接／清理应安全，订阅错误和I/O错误按既定边界分类，不让观察者失败伪装成业务命令失败。

## 正反例与可执行示例

**反例**：把规则挪到一个巨大useOrderEditor后称为业务抽离；仅创建只有字段getter/setter的Order类而所有校验仍在JSX；每render new实例；业务对象直接toast／router.push；Form和对象各持有同一份业务草稿并双向effect同步。

**正例**：OrderEditor持有OrderDraft并通过注入的OrderPort提交；OrderDraft集中数量、行项目及合计规则；视图读取快照并转发业务命令，Hook只稳定实例和桥接订阅。UI字段错误由业务错误码映射；对象本身不决定弹窗样式。

[完整纯TS示例](../examples/order-draft.ts) 展示不可变OrderDraft与受保护快照；[行为测试](../examples/order-draft.test.ts) 验证非法数量、重复项、快照及旧实例不被破坏。数量以整数件为例，不作为金额／重量等字段的统一精度规则。本例不含I/O或订阅；它由任务对象持有并发布变化，不能直接冒充完整React external store。框架适配见 [coding-nextjs](../../coding-nextjs/SKILL.md)。
