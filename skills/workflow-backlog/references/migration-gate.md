# 迁移门禁

判断一个变更是否需要迁移规划才能安全上线，防止需要迁移的变更在迁移方案未就绪前推进到生产环境。

## 迁移触发条件

以下任一情况标记 `需迁移 = 是`：

- 数据库 schema、索引、约束、存储数据形态或 ORM entity 变更。
- Migration 文件、SQL 初始化文件、seed 数据、权限/RBAC 初始化变更。
- 历史数据回填、清洗、重算或一次性运维脚本。
- API 契约需要客户端/服务端协调发布。
- 网关路由归属、鉴权边界或公开入口调整。
- 环境变量、部署脚本、CI/CD 门禁、健康检查、smoke 测试或回滚行为变更。

具体条件可由项目 `.agents/skills-config.json` 的 `release.migrationRules` 扩展或覆盖。

不确定时标记 `待评审`，说明需要检查的内容。

## 阻塞规则

- 需迁移的需求在迁移草稿未完成前，不得推进到 `🧪 Dev Deployed` 之后。
- 迁移草稿转为正式 Release 迁移文档前，需用户选定 Release Key。
- 不得依赖开发环境 ORM 自动同步作为生产可上线的证据。
- 未经用户明确批准，不得执行生产迁移、部署或回滚。

## 执行步骤

### 1. 评估迁移需求

- 对照迁移触发条件，逐项检查当前变更是否命中。
- 在 BACKLOG 备注中写明判断结论和依据。

### 2. 标记迁移状态

- 需迁移：`需迁移 = 是`。
- 无需迁移：`需迁移 = 否`，判断不明显时在备注中说明原因。
- 不确定：`需迁移 = 待评审`，说明需要额外确认的内容。

### 3. 创建迁移草稿（需迁移时）

- 在 `docs/releases/PENDING/MIGRATION-<ID>.md` 创建迁移草稿。
- 文档内容：
  - 变更摘要。
  - 影响的表/服务/配置。
  - 执行步骤。
  - 验证检查。
  - 回滚方案。
  - 关联的 migration/脚本路径。
- 在 BACKLOG 备注中引用迁移草稿路径。

### 4. 维持门禁

- 迁移草稿未完成前，阻止需求状态推进到 `🧪 Dev Deployed` 之后。
- 用户选定 Release Key 后，迁移草稿转入正式 Release 目录。
