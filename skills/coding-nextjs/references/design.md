# 前端设计决策与示例

## 1. 分层、目录与依赖

按业务能力组织模块，目录名沿用项目约定。下表是职责边界，不要求每项都新增目录或文件。

| 边界 | 负责 | 避免 |
|---|---|---|
| 路由／页面 | 权限与路由上下文、服务端取数／页面组装、连接模块 | 堆积所有业务规则、请求、弹窗和样式 |
| 业务编排／状态 | 任务操作、状态迁移、查询键与刷新、失败恢复 | 操作具体 DOM、承担全站万能状态 |
| 展示与交互组件 | 展示、局部交互、输入和语义事件 | 依赖隐含全局状态、直接决定跨模块业务流程 |
| API／适配器 | 传输、认证集成、契约校验、DTO 与业务数据转换 | 操作弹窗、在底层到处弹提示、泄露原始响应 |
| 业务模型／纯逻辑 | 可独立解释的规则、计算、有效状态与转换 | 依赖 React 生命周期、浏览器或网络实现 |

页面组合能力，展示组件经 props／事件协作，业务编排调用 API 接口；业务规则不反向依赖页面或请求实现。共享请求层处理传输共性，业务 API 按资源／能力封装。禁止跨业务模块导入其内部实现；公共出口保持小而明确。

Server／Client 边界按真实项目能力确认：优先在可用的服务端边界完成服务端工作，需要浏览器能力和交互的最小区域进入客户端；跨边界数据可序列化，不把凭据、数据库对象或服务端模块带进客户端。不能把每个页面默认整体标为客户端。

## 2. 抽象、封装与面向对象思维

- 以职责和变化原因拆分，命名能说明业务含义；单个模块应能回答“做什么、输入输出是什么、依赖谁”。
- 先复用已有能力。相同业务语义或明确多个实现才提公共抽象；只有外形相似、规则与生命周期不同的页面保留各自编排。
- 自定义 Hook 封装与 React 状态／生命周期相关的内聚能力；纯转换与计算保持普通函数。避免以一个 `useEverything` 或大量布尔参数隐藏整页复杂度。
- 封装只公开必要 props／操作；内部状态经明确动作修改，不把 setter、完整 store 或可变对象任意暴露给所有调用方。
- 多种变化行为优先组合与小接口；类适合需要维护不变量的领域对象或有明确生命周期的适配器。React 展示不用为“面向对象”改成类组件继承。
- 组件 PascalCase，Hook `useXxx`；动作与事件语义明确，如 `onSubmit`／`onSelectionChange`。布尔表示事实或能力，如 `isSaving`／`canEdit`。文件名遵从项目既有约定，避免无业务语义的 `Common`／`Manager`／`utils` 大杂烩。

**反例**：将订单、客户、库存三页抽成带三十个参数的 `useManageResource`，由 Hook 自行渲染弹窗并访问全局筛选状态。

**正例**：共享分页参数和请求适配器；三页分别持有自身业务操作，复用表格、筛选栏和表单容器。一个本地开关保留组件内状态，无需全局 store 或工厂。

## 3. 状态归属与异步时序

每项可变状态明确事实源、所有者、作用域、更新入口、持久化和失效时机。能由其他状态推导的值直接推导，不用 effect 维护副本。

| 状态 | 默认归属 | 必须明确 |
|---|---|---|
| 服务端数据 | 已有请求／缓存层 | 查询键含所有生效条件及必要用户范围；变更后的失效、刷新或更新 |
| URL 可分享状态 | 路由参数 | 与筛选／页码单向同步规则，默认值和非法参数处理 |
| 输入草稿／表单 | 表单或任务局部 | 初值与编辑身份、dirty、关闭／切换保护、失败保留 |
| 临时交互 | 最近公共组件 | 展开、选择、焦点等的拥有者和重置条件 |
| 跨页面业务／会话 | 明确范围的 Context／store | 为什么需要跨页、登录／登出／权限变化后的清理 |

- 按项目交互区分“草稿筛选”与“已提交筛选”，不得把已确认的提交式查询悄悄改成逐字即时查询。
- 请求取消或序列／身份校验应保证旧响应不覆盖新条件；卸载后清理订阅、定时器与请求。取消不显示为普通业务失败。
- 保存成功后按数据关系更新／失效缓存，避免刷新整个应用；失败保留输入与可重试上下文。
- 连续点击、切换对象、并发保存和返回列表时的状态需定义。前端防重复提交与服务端幂等配合；写请求超时可能已提交，应先按业务契约核对结果再重试。
- 服务端渲染期间的用户数据不得放入跨请求共享的可变单例；用户切换时隔离缓存。

用互斥状态避免不可能的布尔组合，示意：

```ts
type SaveState =
  | { status: 'idle' }
  | { status: 'saving' }
  | { status: 'failed'; message: string }
  | { status: 'saved'; id: string };
```

## 4. 请求、类型与错误边界

API DTO 描述传输契约，表单模型表达可编辑草稿，展示模型表达 UI 语义；字段相同可复用，日期、单位、空值和可选字段语义不同时显式转换。`unknown` 在边界收窄，避免 `as T` 把未经检查的 JSON 变成可信业务类型。明确缺失、null、空字符串与零的区别；关联 ID、枚举和联合类型不滥用自由字符串。

| 失败 | 处理位置 | 用户结果 |
|---|---|---|
| 字段校验 | 表单字段／提交结果映射 | 就地说明、聚焦错误，保留其余输入 |
| 预期业务失败／冲突 | 业务编排 | 展示具体原因、刷新／修改／重试路径 |
| 网络／超时 | 请求层分类，调用方决定恢复 | 保留上下文，按幂等和结果不确定性决定重试 |
| 登录过期／无权限 | 现有认证与权限边界 | 按项目机制恢复登录或说明权限，防止重试循环 |
| 未知／渲染故障 | 适当粒度 Error Boundary／上报边界 | 局部降级及可恢复入口，不让整站无反馈 |

底层保留错误码、可安全展示的信息、必要定位和 cause，界面使用集中映射或项目约定，不直接展示堆栈、SQL 或内部字段。明确由谁提示和上报，避免每层重复 toast／日志。Error Boundary 覆盖渲染子树异常；事件处理和异步请求仍显式处理。页面加载失败与空列表是不同状态。

**反例**：`catch { return []; }`；保存无论成功失败都在 `finally` 关闭并 reset 表单。

**正例**：请求失败保留失败状态；仅成功分支关闭表单并更新列表。字段错误映射表单，未知错误保留关联标识并提供恢复入口。

## 5. 表单模式

- 编辑、创建及对象切换明确模型初始化和重置；服务端刷新不覆盖用户未保存草稿。
- 前端校验改善反馈，服务端仍校验和授权；转换与校验集中，金额、数量、日期按契约保留单位／精度／时区。
- 提交状态阻止重复操作，失败保留内容；提交成功后定义关闭、列表刷新、选择与页码结果。
- dirty 基于真实可编辑内容变化；关闭、返回、切换对象按项目规则保护输入。避免用 `JSON.stringify` 任意对象比较代替明确语义。
- 复用已有表单容器／字段，不把复杂业务条件藏入共享表单基类。

## 6. 界面与交互质量

产品／设计形成方案，前端负责实现与质量检查。通用原则不能覆盖项目已确认偏好；存在冲突时提出具体问题与建议，改变已确认布局、流程或文案按项目机制处理。

| 方面 | 检查方法与合格表现 |
|---|---|
| 任务与信息结构 | 明确用户、对象、目标、入口与结果；按任务组织区块，减少重复上下文、无业务价值介绍与内部实现说明 |
| 重点与层级 | 主要操作及关键状态可发现；位置、字重、留白与语义色共同表达层级，避免全部同权重或过度强调 |
| 文案与文字样式 | 标题／标签／状态使用一致业务术语；按钮表达操作结果且简短，特殊确认文案服从项目规范；字级、颜色与间距沿用语义 Token |
| 流程与反馈 | 主路径顺畅，校验时机恰当；加载、空态、成功、失败、禁用、权限变化有完整反馈；错误说明可执行的下一步 |
| 真实数据与视口 | 长名称、大数据、窄屏、弹窗长内容和滚动不遮挡关键操作；保持项目定义的信息密度和布局 |
| 可访问性 | 标签、键盘、焦点进入／返回与错误定位合理；状态不只靠颜色，文字与控件保持可读可操作 |

**反例**：所有错误显示“系统错误”；状态仅一个红点；用加大标题和介绍填充页面；统一封装后丢失列表条件或后台权限。

**正例**：按项目规范显示具体对象／状态，失败说明原因及下一步，重点操作清楚；在真实页面完成查询→编辑→失败恢复→保存→返回的流程，检查滚动、焦点与状态保留。

## 7. 验证选择

按实际风险验证公开行为：状态迁移、参数转换、过期响应、权限、保存失败与恢复、关键 UI 操作。沿用项目测试工具，不为目录或私有函数形状写镜像测试。UI 需要实际浏览器证据；未验证的视口／交互明确记录。单次抽离同时核查调用方的分页、精度、权限与刷新语义。
